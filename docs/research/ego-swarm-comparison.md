# yopo-restart 与 EGO-Swarm 对照

结论先写在这里。

在 L0 点质量上，yopo-restart 还没有达到 EGO-Swarm 论文里那一档结果。三机、平行槽位、中等林已经能 30/30 到达、碰撞 0。论文仿真的代表场景是 10 架、对向交换、障碍密度 0.14 / 0.28 / 0.42 个/m²、速度上限 2 m/s；实飞是 3 架、约 2 m 的树距、速度上限 1.5 m/s、目标顺序对调，而且感知、规划和飞控都在机上。本仓库最密的一段林是 35 棵树干 / 238 m² = 0.147 棵/m²，三机在这一档是 3/30 到达、撞树 9。冻结的 YOPO 一次前向选候选，做不到论文里那种把轨迹从障碍和邻机上推开的连续优化。

建议先做方案 C：把 `ego-planner-swarm` 留在外部，按它自己的仿真填一张和论文同列的表，同时在 L0 上加一张只报数的对向卡。方案 B（YOPO 当前端、B 样条优化当后段）是 L0 上有可能靠近论文表格的改法，排在这张表之后。方案 A（只在现有候选上加机间代价）对现在的撞树没有对症的证据。PX4 SITL 还没有新方案的数字。实飞不在本仓库范围内，也还没有机载链路。

本文只加文档和一只数几何的脚本。不改规划器，不改冻结门，不改 `docs/tickets.md`。

### 1.3 通信和时间同步

论文有两张网。

- 广播网：新轨迹立刻广播。一条轨迹小于 0.5 KB。正文用蓝牙规格「可以超过 1 Mbps」说明这种包长吃不满带宽，那是标准的上限，不是他们测到的吞吐。另外按固定频率再广播一次，并在收到别人的轨迹时马上做碰撞检查，有风险就重规划。规划前丢掉规划范围外的轨迹。实验里的丢包率、时延、带宽未知。
- 链状网：对时，以及开机时按优先级顺序生成第一条轨迹，避免大家同时在没有邻机信息时出轨迹。对时误差未知。

yopo-restart 的 L0 消息在进程内总线上，可以注入延迟、丢失、重复、乱序。开阔区六机六档（含 drop 20%、乱序加延迟）都是 30/30、碰撞 0、最小机间 2.980 m（[SUMMARY](../results/SUMMARY.md)）。穿林的 Delay Check 是 0，林带没有同一套丢包矩阵。单条消息的字节数未知。时钟是锁步的同一把仿真钟，规划墙钟不推进仿真时间。实机对时未知。

### 1.4 失败模式

论文点名的困难是：障碍不好参数化、感知距离有限、通信不可靠且带宽有限、各自定位带来的漂移。方法上对应四件事：`{p, v}` 碰撞惩罚、隐式拓扑、广播加重规划、深度图里估漂移。

他们给出的失败数字很少。

| 场景 | 论文写了什么 |
|---|---|
| 空域八机交换 | 本方法每架碰撞次数 0。同表里 ORCA 是 0.375 |
| 障碍图十机 | 「each agent belonging to the swarm manages to plan smooth and safe trajectories」。没有到达率，没有碰撞次数，没有失败种子数 |
| 实飞 | 描述了飞过。没有架次数，没有成功率 |
| 局部极小 | 图 3：局部最优会动力学不可行，走廊里会挤。拓扑规划用来离开这些极小 |
| 漂移 | 可以到半米。补偿成立的条件是跟踪误差可以忽略，并且可能相撞的两架里至少一架看得到另一架 |

### 1.5 计算开销

论文基准机是 i7-9700KF。权重 `λ_s = 1.0`，`λ_c = λ_w = λ_t = 0.5`，`λ_d = 0.1`。地图分辨率 0.1 m，地平线 7.5 m。

| 测量 | 数字 |
|---|---|
| 空域八机，单机局部重规划 | 0.514 ms（表 I。离线方法 DMPC 0.668 s、RBP 1.18 s 是整段轨迹的总时间，星号就是为了标明口径不同） |
| 障碍图，密度 0 到 0.42 | 0.49、1.21、2.87、5.00 ms（表 II） |
| 拓扑前端 | 0.017 ms，2 条候选（图 9） |
| 摘要里的说法 | 「only several milliseconds」 |

README 第 5 节：在作者那台 i7-9700KF 上，打开刚体动力学仿真时 15 架是上限，原因是积分太慢，不是规划器。默认因此用 `fake_drone`。第 6 节：规划本身太短，操作系统来不及把 CPU 频率拉高。论文表 II 用的是不是 `fake_drone`，正文和 README 都没有写，未知。

本仓库没有单独的规划耗时。能引用的是整回路墙钟，里面有光线投射、全部飞机的推理、协议和动力学。12e：g2 柱子约 14.5 s 墙钟对 5.26 s 仿真；三机中等林单种子最大约 103 s；六机中等林 seed 0 是 234.2 s 墙钟对 27.08 s 仿真。`docs/ref/minco-port-map.md` 第 14 行有一格写 CPU inference 35–38 ms，那一格标的是另一条移植（表头 uu），不是这次 L0 批跑，不拿来当本仓库的规划耗时。

## 3. 可行性

### 哪些是 YOPO 这种做法本身带的

这些条在「网络和权重不改、仍然一次前向然后选一条多项式」的前提下还在。方案 B 等于在这条前提下外面再加一个优化器，加完之后系统就不再是纯 YOPO。

1. 候选是离散的。密林的结果表里机间距离远大于 0.70 m，撞的是树。选候选只能留下或丢掉已有曲线，不能像论文的碰撞惩罚那样把曲线从树干表面推开。07c 在更早的一次跑里把多数撞树记成走廊 0.05 m 过松或跟踪误差；12e 没有重做类别，机制的分桶对当前 commit 是未知，失败对象是树这一点有结果表。
2. 拓扑逃逸不在网络外面。论文用取反的 `{p, v}` 找另一个局部极小。冻结网络若 15 条里没有一条同时躲开树并留出跟踪余量，重打分也变不出那条曲线。
3. 几何证明要一张网络不提供的地图。影子拒绝率 1.000、主码 `ENV:UNKNOWN`，和飞机其实飞过了可以同时成立。把盾改成硬门，g2 柱子是 0/10。这项不会因为飞得更像 EGO 就自动消失。
4. 已提交的多项式在穿林里不再按邻机未来位置变形。Delay Check 为 0 时，冲突处理是拒绝提案，不是沿邻机轨迹的梯度改控制点。

### 哪些是工程

1. 结果记录里没有规划耗时、没有平均速度。加上这两列不改变轨迹。
2. 现有任务是平行槽位。对向交换可以新加一张卡，不必先改规划器。
3. `forest.py` 只有三档表面净距，表达不了 0.28 和 0.42 个/m²。新几何可以用一张新的场景文件，不必改这三档。
4. 轨迹广播今天是预留和 ACK。要给后段优化用，得另送未来时段上的采样。穿林要不要打开 Delay Check 是协议开关，打开就会改变提交时刻，必须单独重跑，不能和优化器绑在同一张票里。
5. PX4 SITL 上还没有 `upstream`。票 09 的通道连的是另一个仓库的 certified 栈。本仓库不改那个仓库。
6. 对时、VIO、深度图里抹掉邻机、下洗，只在真里程计和真深度上才测得到。L0 真值里程计测不到。
7. 机体半径 0.35 m 对论文的 0.2 m，是场景口径。要和表 II 比最近距离，得在卡上写明半径，并接受这是另一组数。

## 4. 三个方案

### 方案 A：在 YOPO 上加机间代价和轨迹广播

改动：已提交的多项式在总线上按固定周期再发一份采样；提案前用椭球距离做过滤，或者只在已准入的候选里重排。默认关。穿林 Delay Check 仍是 0，除非另开一张票。不改网络，不改 `argmax` 的默认规则，不改 `safe_radius` 默认 0.05 m。

风险：12e 密林的最小机间距离是 4.688 m 以上，碰撞在树上。这张过滤不会消掉那 9 次撞树。若重排改了「首位按上游分数」，就和 ADR 0006 的选择规则不一致，必须先写 ADR。打开 Delay Check 会挪动提交时刻，冻结场景的到达时间可能变。

工作量：一个消息字段、一个默认关的过滤、一张新的对向卡、一轮「旧卡结果不变」的回归。优化器不在这里。

建议：不作为主路径。等对向卡上真的出现机间碰撞，再打开这个开关。

### 方案 B：YOPO 当前端，B 样条优化当后段

改动：一次前向仍产出候选，只用来给优化一个初值或一个绕行方向。COMMIT 前优化一条均匀 B 样条，惩罚里有障碍、邻机椭球、动力学。动力学上限用场景卡的 `a_max = 6`，承诺长度仍要盖住一轮窗口。权重和网络不动。新行为默认关，旧卡走原来的选择。多初值要留着：论文自己用拓扑，就是因为单条局部最优会动力学不可行或挤在一起。

风险：失败模式变成不收敛或停在另一个极小，需要和「选错候选」分开记账。`ego-planner-swarm` 的 README 写许可证是 GPLv3；本仓库根目录没有 LICENSE。复制那份源码要单独处理许可证。按论文式 (1)–(7) 重写，不复制源码。后段即使飞过了，影子盾仍会记 `ENV:UNKNOWN`，不能把拒绝率下降当成优化成功。L0 点质量跟得上，不表示 PX4 跟得上。

工作量：先写接缝（不写求解器），再写单机、无邻机的原型，再写机间惩罚，再跑只报数的对照。四张票分开合。每张都不改已冻卡的 gates。

建议：这是 L0 上有可能把密度和最近距离做到可与表 II 同列比较的做法。开工放在方案 C 的第一张记录之后，避免在仿真口径还没对齐时先写求解器。

### 方案 C：把 ego-planner-swarm 当外部基线，同一张指标表并排

改动：不把那个仓库加进本仓库，不改 `unununnnn/yopo-swarm`。在独立目录按 README 编译，跑它自带的 `simple_run.launch` / `swarm.launch`，把论文表 I、表 II 的列填上：这次运行实际用的是 `fake_drone` 还是 SO3、机数、能否看到规划耗时。本仓库这边只加不进 `suite.txt`、不设 `criteria.frozen` 的场景卡。

风险：两个仿真的数字不能直接比谁更安全。README 的动力学上限 15 架是作者那台 CPU 上的积分开销，不是论文指标。ROS 1 的环境在这台机器上可能不存在；票的完成包括「记下缺哪个包」。论文没给的圆半径、障碍半径、地图边长，卡上写未知，不补一个看起来像的数。

工作量：一张外部运行记录，一张 3 机对向卡（只报数），可选的后续才是 8 机和按密度摆的圆柱场。不改 `yopo_l0` 的选择逻辑。

建议：第一批做这个。没有这张表，方案 A 和方案 B 都是在猜差距来自候选集合还是来自任务形状。
